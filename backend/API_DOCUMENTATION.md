## 1. System Overview & Architecture

MedGraphRAG is a self-verifying, hybrid vector-graph Retrieval-Augmented Generation (RAG) and diagnostic report interpretation system designed for clinical decision support and health literacy.

```
                               ┌──────────────────────────────────────────────┐
                               │             FastAPI Service Layer            │
                               │            (CORS, PyJWT, Lock)               │
                               └──────┬────────────────────────────────┬──────┘
                                      │                                │
                       POST /query, POST /report             POST /features/*
                                      │                                │
                                      ▼                                ▼
                       ┌──────────────────────────────┐ ┌──────────────────────────────┐
                       │    LangGraph Orchestrator    │ │    Feature Service Layer     │
                       │ (Router, Query, Report Nodes)│ │ (MedTrend, CareGap, Coverage)│
                       └──────┬───────────────────────┘ └──────┬───────────────────────┘
                              │                                │
                              ▼                                ▼
        ┌─────────────────────────────────────────────────────────────────────────────┐
        │                                Storage Layer                                │
        ├──────────────────────────────────────────────┬──────────────────────────────┤
        │            Global Knowledge Base             │     Private Patient Store    │
        │                 (READ-ONLY)                  │       (AES-256 / Kùzu)       │
        │ • FAISS Vector Index (2,294,038 vectors)     │ • private_store/<user_id>/   │
        │ • Kùzu Graph DB (2,499,528 nodes)            │ • Isolated encrypted stores  │
        │ • Chunks JSONL & Parquet Sidecar             │ • Ephemeral guest dirs       │
        └──────────────────────────────────────────────┴──────────────────────────────┘
```

## 3. Authentication & Session Management

### JWT Bearer Authentication
All protected routes require an HTTP Authorization header containing a standard JWT Bearer token:
```http
Authorization: Bearer <JWT_ACCESS_TOKEN>
```
* **Algorithm**: `HS256`
* **Default Expiration**: `60 minutes` (configurable via `MEDGRAPH_JWT_EXPIRE_MINUTES`)
* **Payload Claims**:
  ```json
  {
    "sub": "demo_user",
    "user_id": "demo_user",
    "role": "user",
    "ephemeral": false,
    "exp": 1755255600
  }
  ```

### User Roles & Access Levels
* **`user`**: Standard authenticated user. Can query the global knowledge base, upload private lab reports, access personal longitudinal trends, and reconcile care gaps.
* **`admin`**: Administrative user account.
* **`guest`**: Ephemeral visitor account created via `POST /auth/guest`. Assigned temporary user ID `guest_<12_hex_chars>`.

### Ephemeral Guest Sessions & Auto-Purge
1. **Creation**: `POST /auth/guest` generates an isolated workspace at `private_store/guest_<uuid>/`.
2. **Explicit Purge**: Calling `POST /auth/logout` with a guest token immediately deletes `private_store/guest_<uuid>/` from disk via `shutil.rmtree()`.
3. **Startup Sweep**: During application startup lifespan (`purge_stale_guest_directories()`), any `guest_*` directory older than `jwt_expire_minutes` is automatically purged.

### Destination Isolation & Security (403 Rules)
In `POST /query`, the `destination` parameter defines which data store is retrieved:
* Valid values:
  * `"global"`: Searches only the global read-only knowledge base.
  * `<user_id>` or `private_store/<user_id>`: Searches the authenticated user's private store.
* **Security Enforcement**: If an authenticated user passes a `destination` targeting another user's private store, the backend rejects the request immediately:
  * **HTTP Status**: `403 Forbidden`
  * **Response Body**:
    ```json
    {
      "detail": {
        "error": "forbidden_destination",
        "detail": "You are not authorized to query another user's private store."
      }
    }
    ```

* **Response 200 OK**:

### POST /query
Executes the self-verifying hybrid RAG pipeline across vector and knowledge graph indices.

* **Method**: `POST`
* **Path**: `/query` (or `/api/v1/query`)
* **Auth Required**: **Yes** (`Bearer <token>`)
* **Request Content-Type**: `application/json`
* **Request Fields**:
  | Field | Type | Required | Default | Description |
  | :--- | :--- | :---: | :---: | :--- |
  | `query` | `string` | **Yes** | N/A | Natural language clinical or biomedical query ($\ge 3$ characters). |
  | `destination` | `string` | No | `"global"` | Retrieval target space (`"global"` or user's own `user_id`). |

* **cURL Example**:
  ```bash
  curl -X POST http://localhost:8000/query \
    -H "Authorization: Bearer <TOKEN>" \
    -H "Content-Type: application/json" \
    -d '{
      "query": "potassium hyperkalemia ECG changes peaked T waves treatment",
      "destination": "global"
    }'
  ```

* **Response 200 OK**:
  | Field | Type | Description |
  | :--- | :--- | :--- |
  | `route` | `string` | Routed intent: `"medical_query"`, `"knowledge_graph"`, or `"out_of_scope"`. |
  | `answer_text` | `string` | Fully grounded answer citing evidence as `[E1]`, `[E2]`, etc. |
  | `answer_status` | `string` | Verification verdict: `"verified"`, `"caution"`, `"uncertain"`, `"contradiction_detected"`, `"refusal"`, `"out_of_scope"`. |
  | `confidence_tier` | `string` | Overall confidence tier: `"high"`, `"medium"`, or `"low"`. |
  | `final_confidence` | `float` | Weighted confidence score ($0.0 \le c \le 1.0$). |
  | `citations` | `array[object]` | Structured provenance list for cited chunks. |
  | `citations[].label` | `string` | In-text citation label (e.g., `"[E1]"`). |
  | `citations[].chunk_id` | `string` | Unique chunk identifier. |
  | `citations[].document_id` | `string` | Source document identifier. |
  | `citations[].source` | `string` | Source dataset folder (e.g. `"Clinical_practice_guidlines"`). |
  | `citations[].category` | `string` | Document category (`"guideline"`, `"drug"`, `"research_paper"`). |
  | `citations[].snippet` | `string` | Text snippet included in prompt. |
  | `citations[].fused_score` | `float` | Reciprocal Rank Fusion score. |
  | `citations[].source_type` | `string` | Retrieval origin: `"faiss"`, `"graph"`, or `"both"`. |
  | `graph_paths` | `array[string]` | Formatted human-readable knowledge graph traversal paths. |
  | `disclaimer_present` | `boolean` | `true` if mandatory physician disclaimer is included. |
  | `retry_count` | `integer` | Number of verification retry cycles performed ($0 \le r \le 2$). |
  | `latency_breakdown` | `object` | Latency breakdown in milliseconds (`router`, `retrieval`, `context`, `llm`, `verification`, `total`). |

### POST /report
Uploads and interprets diagnostic lab reports across multiple formats (PDF, PNG, JPG, XLSX, CSV). Results are normalized against LOINC ontology, checked against critical reference ranges, and persisted into the user's private store.

* **Method**: `POST`
* **Path**: `/report` (or `/api/v1/report`)
* **Auth Required**: **Yes** (`Bearer <token>`)
* **Request Content-Type**: `multipart/form-data`
* **Request Fields**:
  | Form Field | Type | Required | Allowed File Types | Max Size |
  | :--- | :--- | :---: | :--- | :--- |
  | `file` | `UploadFile` (binary) | **Yes** | `.pdf`, `.png`, `.jpg`, `.jpeg`, `.xlsx`, `.csv` | `20 MB` |

* **cURL Example**:
  ```bash
  curl -X POST http://localhost:8000/report \
    -H "Authorization: Bearer <TOKEN>" \
    -F "file=@/path/to/lab_report.pdf"
  ```

  | Field | Type | Description |

### POST /features/coverage

## 6. Complete Schema Specifications

### TrendResult & Associated Schemas
* **`TrendResult`**: Root response for `POST /features/trend`.
* **`TrendItem`**: Longitudinal trajectory summary per lab test.
* **`LabMeasurement`**: Chronological measurement point with reference boundaries.
* **`GraphCausePath`**: Formatted graph path connecting test to associated disease entity.
* **`TrendDirection`** (`enum`):
  * `"worsening"`: Negative clinical drift or crossing above/below normal reference bounds.
  * `"improving"`: Favorable movement back toward normal physiological baseline.
  * `"stable"`: Minimal fluctuation within normal limits ($|\Delta| \le \text{threshold}$).
  * `"new"`: First observed measurement for this test.
  * `"resolved"`: Value previously abnormal that has returned to normal range.

### CareGapResult & Associated Schemas
* **`CareGapResult`**: Root response for `POST /features/caregap`.
* **`GapItem`**: Clinical discrepancy item.
* **`GapType`** (`enum`):
  * `"out_of_target"`: Lab value exceeds evidence-based clinical guidelines (e.g. $\text{HbA1c} > 7.0\%$).
  * `"missing_recommended_check"`: Standard guideline-recommended panel test not found in recent report.

### CoverageMap & Associated Schemas
* **`CoverageMap`**: Root response for `POST /features/coverage`.
* **`SubQuestionCoverage`**: Coverage metrics and rephrase suggestions per atomic sub-question.
* **`CoverageClass`** (`enum`):
  * `"strong"`: $\text{fused\_score} \ge 0.12$ AND $\text{distinct\_docs} \ge 2$.
  * `"partial"`: $0.03 \le \text{fused\_score} < 0.12$ OR ($\text{fused\_score} \ge 0.12$ and $\text{distinct\_docs} == 1$).
  * `"none"`: $\text{fused\_score} < 0.03$ or $0$ evidence chunks retrieved.

### VerifiedAnswerResult & Associated Schemas
* **`VerifiedAnswerResult`**: Root response payload returned in `final_response` by `POST /query`.
* **`answer_status`** (`enum`):
  * `"verified"`: All extracted claims supported by cited evidence; high confidence.
  * `"caution"`: Medium confidence or partial claim support; review citations carefully.
  * `"uncertain"`: Low evidence confidence after retries; prepends uncertainty disclosure.
  * `"contradiction_detected"`: Verified contradiction found between model answer and retrieved evidence.
  * `"refusal"`: Pipeline explicitly refused to answer due to insufficient evidence.
  * `"out_of_scope"`: Non-medical inquiry rejected by router.
  * `"error"`: Pipeline execution exception fallback.
* **`confidence_tier`** (`enum`):
  * `"high"`: $\text{final\_confidence} \ge 0.75$.
  * `"medium"`: $0.50 \le \text{final\_confidence} < 0.75$.
  * `"low"`: $\text{final\_confidence} < 0.50$.

## 7. Frontend Integration Guide

### CORS Configuration & Base URLs
The backend permits credentials and requests from the following origin domains:
* `http://localhost:3000`
* `http://127.0.0.1:3000`
* `http://localhost:8000`
* `http://127.0.0.1:8000`

### Token Storage & Request Interceptors
1. Upon successful login (`POST /auth/login` or `POST /auth/guest`), store `token` in memory or `sessionStorage`.
2. Attach an HTTP interceptor to add `Authorization: Bearer <token>` to all subsequent requests.
3. If an endpoint responds with `401 Unauthorized`, clear the stored token and redirect to `/login`.

### Multipart File Upload Contract
When calling `POST /report`, send a `FormData` object with the field name **`file`**:
```typescript
const formData = new FormData();
formData.append("file", fileObject, fileObject.name);

const response = await fetch("/report", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${token}`
  },
  body: formData
});
```

### Rendering Interactive [E#] Citations
In `POST /query` responses, the LLM incorporates bracketed citations (e.g., `[E1]`, `[E2]`).
1. Use a regex to match `\[E(\d+)\]` tags in `answer_text`.
2. Replace matched tags with clickable citation chips or hover tooltips.
3. Link the chip to the matching element in `citations` where `label === "[E" + index + "]"`.
4. Render a popover displaying:
   * **Source**: `citation.source`
   * **Document**: `citation.document_id`
   * **Category**: `citation.category`
   * **Snippet**: `citation.snippet`
   * **RRF Score**: `citation.fused_score.toFixed(4)`

### Confidence Tiers & Visual Styling
* **`high`** ($\ge 0.75$): Display a green badge (e.g., `🟢 High Confidence (88%)`).
* **`medium`** ($0.50 - 0.74$): Display a yellow badge (e.g., `🟡 Medium Confidence (62%)`).
* **`low`** ($< 0.50$): Display an amber/red warning banner recommending physician consultation.

### Critical Value Escalation Banners
When rendering diagnostic report responses (`POST /report`), check if `answer_text` begins with `⚠️ URGENT CLINICAL NOTICE` or contains critical classifications (`CRITICAL_HIGH`, `CRITICAL_LOW`). Render a prominent, persistent red emergency alert box at the top of the viewport advising immediate medical attention.

### Mandatory Medical Disclaimer Display
Every screen rendering output from `/query`, `/report`, or `/features/*` **MUST** display the standard disclaimer:
> *"This is information, not medical advice — consult your physician."*

### Feature UI Rendering Guidelines
* **MedTrend (`/features/trend`)**:
  * Render a longitudinal data table showing `test_name`, `earliest_value`, `latest_value`, `delta`, and `rate_per_month`.
  * Highlight rows where `is_significant === true` with a caution icon (⚠️) and show `significance_reason`.
  * Render an interactive sparkline line chart connecting `measurements[].report_date` and `measurements[].value`, with dashed horizontal lines for `ref_low` and `ref_high`.
* **CareGap (`/features/caregap`)**:
  * Render two separate card decks: **Out-of-Target Values** (⚠️ Red/Amber) and **Missing Recommended Checks** (🔍 Blue/Slate).
  * In each card, display the `guideline_target` and expandable `guideline_provenance` citation snippets.
* **Evidence Coverage Map (`/features/coverage`)**:
  * Display overall coverage status (`STRONG` / `PARTIAL` / `NONE`).
  * Render sub-questions as accordion rows color-coded by `coverage_class`:
    * `strong`: Green pill (`Strong Evidence`).
    * `partial`: Yellow pill (`Partial Evidence`) with `suggested_rephrase` copy button.
    * `none`: Red pill (`No Direct Evidence`) with suggested rephrase chips.

## 8. Known Runtime Behaviors & Hardware Budgets

### Cold vs. Warm Startup & Lazy LLM Initialization
* At server startup, the retrieval singletons (`FAISS`, `Kùzu`) warm up on CPU memory (~1.2 GB RAM).
* The GGUF LLM weights are **NOT** loaded at startup (`llm_loaded === false` in `GET /health`), preserving 0 MB GPU VRAM.
* The first execution of `/query` or `/features/coverage` initializes the LLM into GPU VRAM (taking ~15–24 seconds for the cold invocation). Subsequent requests execute warm in ~1.5–7.9 seconds.

### Single-Flight LLM Serialization Lock
* To prevent GPU out-of-memory crashes on hardware with 6 GB VRAM, all LLM invocations are serialized via a global `asyncio.Lock` (`get_llm_lock()`).
* If multiple concurrent requests arrive at `/query`, `/report`, or `/features/coverage`, they queue gracefully and execute sequentially without dropping connections.
